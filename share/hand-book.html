01

Những điều cần biết khi mới vào team

Mục tiêu: biết tìm thông tin ở đâu, setup môi trường và hiểu process trước khi nhận task thực tế.

1

Hiểu project

Đọc overview hệ thống, business domain, architecture, repo chính và luồng deploy.

2

Setup môi trường

Clone repo, setup account, VPN, DB, Docker, IDE và chạy project local.

3

Hiểu process

Nắm task flow, DD, coding convention, branch rule, PR rule, review và test.

Nguyên tắc chung: Không bắt đầu code khi requirement, phạm vi ảnh hưởng hoặc hướng xử lý còn chưa rõ. Nếu chưa chắc chắn, cần xác nhận với PM / Leader / Reviewer trước.
An toàn thông tin: Không đưa password, token, file .env, dữ liệu production hoặc thông tin khách hàng vào ticket, DD, PR hay source code. Dùng secret manager và dữ liệu đã được che/masked theo quy định của team.

04

Cách làm DD (Design Document)

DD cần giúp reviewer hiểu tại sao thay đổi, thay đổi ở đâu và hệ thống sẽ hoạt động như thế nào sau thay đổi.

Trước khi viết DD

  • Đọc toàn bộ requirement / ticket / Figma / tài liệu liên quan.
  • Xác định current behavior và expected behavior.
  • Kiểm tra code hiện tại để biết module, API, DB, batch/job hoặc service bị ảnh hưởng.
  • Liệt kê các điểm chưa rõ và confirm trước khi chốt solution.
  • Xác định backward compatibility, migration hoặc dữ liệu cũ có bị ảnh hưởng không.

Cấu trúc DD khuyến nghị

PhầnNội dung cần có
1. OverviewMục tiêu task, vấn đề cần giải quyết, link requirement/ticket.
2. ScopeIn scope / Out of scope.
3. Current BehaviorHệ thống hiện tại đang hoạt động như thế nào.
4. Proposed SolutionGiải pháp dự kiến, flow chính và lý do chọn giải pháp.
5. ImpactRepo, module, API, DB, queue, batch, cache, UI hoặc service bị ảnh hưởng.
6. API / DB ChangeRequest/response, schema, query, migration, index hoặc compatibility.
7. Error HandlingCác case lỗi, retry, validation, timeout và fallback.
8. Test PointsHappy path, edge case, negative case, regression area.
9. RollbackCách rollback hoặc xử lý nếu release có vấn đề.
10. Open QuestionsCác nội dung chưa confirm hoặc cần quyết định thêm.

06

Quy trình develop

Bắt đầu khi task đã Ready. Mục tiêu của phần này là biến solution đã chốt thành thay đổi có thể review, test và release an toàn.

  1. Chuẩn bị workspace
    Tạo branch theo convention, đồng bộ base branch và kiểm tra môi trường local. Ví dụ feature/TASK-123-short-description.
    Branch & commit convention ↗
  2. Implement đúng scope
    Code theo DD/requirement và coding convention; không tự mở rộng scope. Nếu solution khác DD, dừng để cập nhật và re-review.
    Coding convention ↗
  3. Self review
    Kiểm tra diff trước khi push: không còn debug code, secret, thay đổi ngoài scope, lỗi naming hoặc error case bị bỏ sót.
    Checklist trước PR ↗
  4. Test & lưu evidence
    Chạy unit/integration/manual test theo test points; lưu log, ảnh hoặc kết quả cần thiết để QA/reviewer kiểm tra lại.
    Test plan / evidence template ↗
  5. Tạo Pull Request
    Nêu mục tiêu, thay đổi, impact, cách test và link ticket/DD. Chỉ request review khi pipeline bắt buộc đã pass.
    PR template ↗
  6. QA / regression / release
    Hỗ trợ QA, xác nhận regression area, migration/config và rollback plan trước khi release theo quy trình team.
    Release & rollback runbook ↗
  7. Đóng task
    Sau khi merge/release đúng môi trường, cập nhật ticket với link PR, test evidence, note deploy và follow-up/known issue (nếu có).
    Checklist đóng task ↗
Definition of Done: Code đúng scope đã được review và merge; các kiểm tra bắt buộc đã pass; test evidence, tài liệu/DD và ticket đã cập nhật; migration/config/release note (nếu có) đã được bàn giao rõ ràng.
07

Review

Review là điểm kiểm soát để xác nhận solution hoặc code phù hợp với requirement; team áp dụng quy ước review hiện hành, không hướng dẫn chi tiết theo step tại đây.

Khi gửi review: đính kèm ticket/DD, tóm tắt thay đổi, impact và test evidence; nếu feedback làm đổi solution thì cập nhật DD trước khi tiếp tục.

Test & Fix bug

Không chỉ test happy path; cần chú ý negative case, boundary và regression.

Happy PathLuồng chính hoạt động đúng như requirement.
Negative CaseInput sai, thiếu quyền, sai trạng thái, lỗi dependency.
BoundaryMin/max, empty/null, duplicate, large data.
RegressionChức năng cũ liên quan vẫn hoạt động bình thường.

10

Checklist nhanh

Dùng như checklist cuối mỗi phase để giảm lỗi bỏ sót.

Trước khi bắt đầu code

  • Đã hiểu requirement.
  • Đã confirm open questions.
  • Đã xác định impact.
  • DD đã được review nếu cần.
  • Branch đúng convention.

Trước khi tạo PR

  • Self review diff.
  • Không còn debug code.
  • Test pass.
  • DD khớp implementation.
  • PR description đầy đủ.

Trước khi merge

  • Review comment đã xử lý.
  • Pipeline pass.
  • Không còn unresolved discussion.
  • QA / test evidence đầy đủ nếu yêu cầu.
  • Migration/config đã sẵn sàng.

Trước khi đóng task

  • Code đã merge/release đúng môi trường.
  • Ticket được cập nhật trạng thái.
  • Tài liệu/DD được cập nhật cuối cùng.
  • Không còn follow-up hoặc known issue chưa ghi nhận.

FAQ cho member mới

Một số câu hỏi thường gặp trong quá trình làm việc.

Task nhỏ có cần DD không?

Tùy rule của team. Có thể bỏ DD với thay đổi nhỏ, rõ ràng và ít impact. Nhưng thay đổi business logic, DB, API hoặc nhiều module nên có DD.

Đang code mới phát hiện solution trong DD không phù hợp thì sao?

Dừng ở điểm cần quyết định, cập nhật DD, nêu rõ lý do và confirm/re-review trước khi tiếp tục nếu thay đổi lớn.

Khi nào cần hỏi Leader/Reviewer?

Khi requirement chưa rõ, có nhiều solution, impact lớn, thay đổi architecture, có risk production hoặc estimate có khả năng lệch đáng kể.

Có nên refactor code ngoài phạm vi task không?

Chỉ nên làm khi cần thiết và đã thống nhất. Tránh mở rộng scope không cần thiết vì làm tăng review effort và regression risk.
